# Quality parity

The gate this repository is measured against is the one on
[jellyfin-plugin-sso](https://github.com/iderex/jellyfin-plugin-sso). Every
workflow there is either adopted here or declined here, and every difference in
either direction carries one line of reasoning. A difference nobody wrote a line
for is a defect. A difference with a line is a decision.

This document is the reasoning. It is not the gate. What the gate requires is
printed by the commands below, and where the two disagree the commands are
right.

## What each gate actually requires

The other board:

    $ gh api repos/iderex/jellyfin-plugin-sso/rules/branches/main \
        --jq '.[] | select(.type=="required_status_checks")
              | .parameters.required_status_checks[].context'
    build
    ABI floor build
    Package (JPRM) / Build package
    Package (JPRM) / Generate SBOM
    CodeQL
    Analyze (csharp)
    DCO sign-off
    Deterministic PR-hygiene checks
    Enforce greppable invariants
    Reject Trojan Source Unicode
    Audit workflows (zizmor)
    prettier
    dependency-review

This one:

    $ gh api repos/iderex/jellyfin-plugin-requests/rules/branches/master \
        --jq '.[] | select(.type=="required_status_checks")
              | .parameters.required_status_checks[].context'
    call / build
    call / test
    Reject Trojan Source Unicode

Thirteen contexts against three. Ten of the thirteen have an adopted row below
and no context here yet, which is the distance this milestone closes.

## One row per workflow here that the table above does not already place

Seven files here map one to one onto a file there and are covered by their row
above: `dco.yml`, `dependency-review.yml`, `publish.yaml`, `scan-codeql.yaml`,
`scorecard.yml`, `unicode-guard.yml` and `zizmor.yml`. The six below are the
rest. Six plus seven is the thirteen files in `.github/workflows/`, so every
file in this tree is placed by one table or the other.

The first two do have a counterpart there and are listed here anyway, because
what they are is not what it is: they are calls into shared workflows owned
somewhere else, and the row is about that rather than about the capability.

| File here | Disposition | Reasoning |
| --- | --- | --- |
| `build.yaml` | replaced, #22 | It calls a shared workflow that knows nothing about this plugin's multi-targeting, its lockfiles or its analyzer settings, and it packages only the first of two claimed lines. |
| `test.yaml` | replaced, #22 | Same call, same blindness, and it is one half of the pair the required set names. |
| `changelog.yaml` | reviewed, #21 | #107 makes the changelog a gated obligation, so this either serves that or is removed rather than left running against a scheme nobody has fixed yet. |
| `command-dispatch.yaml` | reviewed, #21 | It is template automation that turns issue comments into workflow runs, and it stays only if this repository decides it wants that surface. |
| `command-rebase.yaml` | reviewed, #21 | Same automation, the half that rewrites pull request branches on command, and the same condition applies. |
| `sync-labels.yaml` | reviewed, #21 | The label vocabulary here is maintained on the tracker, so a workflow that overwrites it from a file elsewhere is adopted deliberately or removed. |

The four rows marked reviewed are reviewed here and not decided here. Each is
inherited automation for a way of working this repository has not chosen, none
of them is in the required set, and none of them refuses anything, so leaving
them running costs nothing that a later decision cannot undo. What is not
acceptable is leaving them undescribed, which is what this table fixes.

## What this document does not do

It records no evidence that any guard bites. Every row above says what a
workflow is for, and none of them says it was watched failing for that reason.
That is #25 for the five that arrived with this repository, and each adopted row
owes the same thing at the issue that builds it.

Nothing here is enforced. No check reads this file, no check compares it against
the workflow directory, and a workflow added or deleted without a row moves
nothing red. The table drifts against the thing it describes the moment either
board changes, and the commands at the top are the only part that cannot.
